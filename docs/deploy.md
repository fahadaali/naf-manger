# النشر — طريقٌ واحد لا اثنان

**المنصة تُنشر من GitHub Actions حصراً** — `.github/workflows/deploy.yml`،
عند كل دفعة إلى `main`. وهذا هو النمط نفسه في `naf-id`.

---

## لماذا لا يصلح ربطُ Cloudflare بالمستودع

لـ Cloudflare نظامُ بناءٍ خاص — **Workers Builds** — يُربط بمستودع GitHub
من لوحة العامل، فيبني وينشر عند كل دفعة. وكان مربوطاً بهذا المستودع،
فصار على العامل ناشران يتسابقان على كل دفعة.

وهو **لا يصلح لهذه المنصة**، لا لأنه أضعف بل لأنه لا يستطيع:

| الخطوة | Workers Builds | GitHub Actions |
|---|:---:|:---:|
| بناء الواجهة | ✓ | ✓ |
| `wrangler deploy` | ✓ | ✓ |
| تطبيق هجرات D1 | ✗ | ✓ |
| إنشاء KV و R2 وحقن معرّفاتها | ✗ | ✓ |
| حقن بريد الآدمن | ✗ | ✓ |
| رفع `AUTH_CLIENT_SECRET` | ✗ | ✓ |

والثلاثة الأخيرة تحتاج رمز واجهةٍ برمجية للحساب، ولا يملكه بيئةُ البناء
في Cloudflare — لها رمزُ بناءٍ لا غير. فالنقص بنيويّ لا يُسدّ بإعداد.

**وأخطرُ ما فيه أن فشله ليس أسوأ حالاته.** `wrangler.toml` في المستودع
يحمل `REPLACE_WITH_D1_ID` و`REPLACE_WITH_KV_ID` نائبَين يملؤهما السير عند
النشر. فناشرٌ يأخذ الملفّ كما هو من المستودع يهبط بارتباطاتٍ مكسورة
**ونشرةٍ تبدو ناجحة**: الأصول تُرفع، والعامل يعمل، وأولُ نداءٍ يمسّ
القاعدة يسقط بخطأ ارتباطٍ لا يذكر السبب.

ولذلك في السير خطوةُ **«التحقق من اكتمال الارتباطات»**: لا يُنشر ملفٌّ
بقي فيه نائب.

## إن ظهر «Latest build failed» في لوحة Cloudflare

رسالتُه:

> The build token selected for this build has been deleted or rolled and
> cannot be used for this build. Please update your build token…

**لا تُحدّث الرمز.** الرمزُ الميت هو ما يمنع الضرر: إحياؤه يجعل كل دفعةٍ
نشرتين متسابقتين، وإحداهما بلا هجرات وبارتباطاتٍ ناقصة.

**والعلاج فصلُ الربط:**

> Workers & Pages → `naf-manger` → Settings → Build →
> Git repository → **Disconnect**

وبعده تختفي البناءاتُ الفاشلة، ويبقى النشر من GitHub وحده.

## ما يلزم في أسرار المستودع

| السرّ | لماذا |
|---|---|
| `CLOUDFLARE_API_TOKEN` | أربع صلاحيات — انظر رأس `deploy.yml` |
| `CLOUDFLARE_ACCOUNT_ID` | الحساب |
| `CF_D1_DATABASE_ID` | تُقصد القاعدة بمعرّفها لا باسمها |
| `AUTH_CLIENT_SECRET` | سرّ المنصة عند المركز |
| `BOOTSTRAP_ADMIN_EMAIL` | الآدمن الأول — **قبل أول دخولٍ لصاحبه** |
| `VITE_GEMINI_API_KEY` | اختياريّ — المساعد الذكي وحده يقرؤه |

و`NAF_PACKAGES_TOKEN` اختياريّ: `naf-auth` مستودعٌ عامّ، والسير يحوّل جلبَه
إلى `https` بلا اعتماد. ويُقرأ الرمزُ إن وُجد ليبقى السير عاملاً لو صار
المستودع خاصاً.

## مخطّط القاعدة — ثمانية جداول لا تاسعَ لها

| الجدول | ما يحمله |
|---|---|
| `members` | العضوية والأدوار — مرجعُ الصلاحيات في كل طلب محروس |
| `clients` | العملاء |
| `prospects` | العملاء المحتملون |
| `marketers` | المسوّقون |
| `cases` | القضايا |
| `activity_logs` | سجلّ الأنشطة |
| `system_settings` | إعدادات النظام — كائنٌ واحد تحت مفتاح `settings` |
| `commission_payments` | دفعات العمولات |

وهي مجموعُ `migrations/0001_members.sql` و`0002_platform_tables.sql`،
ويطبّقها السير في خطوة **«تطبيق الهجرات»** عند كل نشرة.

**ولا يلزم تشغيلُ شيءٍ يدوياً في الأحوال العادية.** أمّا حين تُنشأ قاعدةٌ
جديدة بلا سير — أو يُراد التحقّق من اكتمال المخطّط — ففي
[`docs/d1-console.sql`](./d1-console.sql) النصُّ كلُّه في ملفٍّ واحد يُلصق في
Console D1 كما هو. وتشغيلُه آمنٌ للتكرار: كل جملةٍ فيه `IF NOT EXISTS`،
ولا `DROP` فيه ولا `DELETE`.

    Dashboard → Storage & Databases → D1 → naf-manger → Console

أو من الطرفية:

```sh
npx wrangler d1 execute naf-manger --remote --file=docs/d1-console.sql
```

### ما ليس في القاعدة عن قصد

اجتماعات Zoom لا جدولَ لها: `ZoomMeetingModal` يحفظها في `localStorage`
المتصفّح، فهي لصاحب الجهاز وحده ولا يراها زميلُه. والتقارير المخصّصة
والتنبؤات والاستبصارات أغلفةٌ فارغة في `database.ts` — لا جدول لها ولا
مسار. وكلاهما بناءٌ جديد لا نقصٌ في المخطّط، فلا يُنشأ لهما جدولٌ قبل أن
يُكتب ما يقرؤه.
